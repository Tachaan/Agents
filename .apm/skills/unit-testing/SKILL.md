# 単体テスト工程スキル（Unit Testing）

> 本スキルは **V字ウォーターフォール型開発を前提とした汎用工程ガイド** である。
> 成果物のパス・ファイル名・テスト/証跡コマンド・テストフレームワークは、適用するプロジェクトの
> 規約・技術スタックに合わせて読み替えること。本文中のパスやコマンドは推奨例であり、固定値ではない。

## V字モデルにおける位置づけ

単体テストはV字ウォーターフォールモデルの最初のテスト工程です。対向設計工程は**詳細設計**であり、
詳細設計書に記載されたモジュール・メソッド単位の仕様を検証します。

```
要件定義 ─────────────────────────────── システムテスト
    └─ 基本設計 ───────────────── 結合テスト
         └─ 詳細設計 ★ ──── 単体テスト ★
              └─ 実装 ─┘
```

## 成果物（汎用）

| 成果物 | 推奨パス（例） |
|--------|------|
| テスト仕様書 | `docs/<単体テスト>/UTS-XXX_単体テスト_テスト仕様書.md` |
| テスト結果報告書 | `docs/<単体テスト>/UTR-XXX_単体テスト_テスト結果報告書.md` |
| カバレッジ証跡 | `docs/<単体テスト>/coverage_<コンポーネント>/` |
| 実行ログ証跡 | `docs/<単体テスト>/evidence/` |

### テスト仕様書の構成（標準）

- 文書管理
- UT対象一覧
- モック・スタブ方針
- カバレッジ計画
- テストケース一覧
- テストケース詳細
- 観点・トレーサビリティ

## テスト実行（汎用）

- プロジェクトの **単体テストコマンド** を実行する
  （例 Maven: `mvn test` ／ Node: `npm test` ／ .NET: `dotnet test` ／ Go: `go test ./...`）
- 結合テストと分離する構成では、単体テストのみを対象とするパターン指定を用いること
- カバレッジレポートを生成する設定を有効化すること（例: JaCoCo, V8/Istanbul, coverlet など）

## 作業フロー（必須チェックリスト）

以下のステップを **上から順に** 実行すること。ステップを飛ばしてはならない。

---

### Step 1: 上流工程仕様書を参照し、テスト対象を特定する

- 詳細設計書を読み、今回の実装対象となるモジュール・メソッドを特定する
- 内部API仕様書からAPIエンドポイントの入出力仕様を把握する
- 実装差分（直近のMerge Commitの変更ファイル）から対象スコープを絞り込む

---

### Step 2: テスト仕様書を更新する

**更新対象:** テスト仕様書（テストケース一覧）

**実施内容:**
- 新規テストケースを追記する（ID採番: 推奨 `TC-UT-XXX` の連番）
- 各行に以下を記入: テストケースID / 対象モジュール / メソッド / 観点 / 重要度 / 前提条件 / 期待結果概要 / テスト手法 / ステータス
- 正常系・異常系・境界値の3観点を網羅すること

---

### Step 3: テストコードを実装する

**実施内容:**
- プロジェクトのテストフレームワークでテストコードを作成する
  （例 バックエンド: JUnit + Mockito ／ フロントエンド: Vitest/Jest + Testing Library）
- テストメソッド名・タイトルにテストケースIDを含める
- AAA パターン（Arrange-Act-Assert）に従う

---

### Step 4: テストを実行し、全件合格を確認する

- 単体テストコマンドを実行する
- **全件合格（失敗 0・エラー 0）** であることを確認する
- 1件でも失敗がある場合はテストコードまたは実装を修正して再実行する

---

### Step 5: 証跡を成果物ディレクトリ内に格納する

下記「証跡の収集手順」に従い、カバレッジレポート・実行ログを成果物ディレクトリにコピーし、
ファイルが存在することを確認する。

---

### Step 6: テスト結果報告書を更新する

**更新対象（必須）:**
- 実施結果一覧（ケースID / 実施日 / 結果 / 証跡パス）
- 結果サマリ（総件数・合格率・合否判定）
- カバレッジ実績（新規モジュールの数値）

**不具合があった場合のみ:** 不具合一覧

---

### Step 7: Rubber-Duck Agent を実行する

下記「Rubber-Duck 実行手順」に従い、`rubber-duck` エージェントを起動してレビューを受ける。

---

### Step 8: 指摘事項を修正し、工程完了とする

- Blocking 指摘があればコード・ドキュメントを修正し、テストを再実行する
- 修正完了後、git commit する

---

> **WARNING:** Step 5（証跡格納）と Step 7（Rubber-Duck）を実行せずに工程を完了してはならない。

## 証跡の収集手順（汎用）

テスト実行後、生成された証跡を成果物ディレクトリ配下にコピーすること。

- **カバレッジレポート（HTML）**: テストツールの出力先（例: `target/site/jacoco/`,
  `coverage/`）を `docs/<単体テスト>/coverage_<コンポーネント>/` にコピーする
- **テスト実行ログ（XML/TXT）**: レポート出力先（例: `surefire-reports/`, JUnit XML）を
  `docs/<単体テスト>/evidence/` にコピーする

証跡が成果物配下に存在しない状態でテスト結果報告書を更新してはならない。

## 作業ガイドライン

### 上流工程仕様書の参照（V字対応：詳細設計）

単体テストはV字モデルで **詳細設計** と対応する。テスト設計の入力として、詳細設計書・内部API仕様書を
必ず参照し、各メソッドの入出力・分岐・例外を、正常系／異常系／境界値の観点でテストケースに
落とし込むこと。

### テスト結果と証跡の一対管理

テスト結果報告書と証跡（エビデンス）は **必ず一対** で残すこと。証跡は成果物ディレクトリ内に格納し、
各テストケースIDと証跡ファイルを対応付け、後から追跡できるようにすること。

### 出力フォーマット

- ドキュメントはMarkdown形式で作成
- ファイル命名規則（推奨）: `UTS-XXX_<名>.md`（仕様書）/ `UTR-XXX_<名>.md`（報告書）

## 完了条件（Exit Criteria）

本工程は以下の **すべて** を満たした場合にのみ完了とする。1つでも欠けている場合は工程未完了である。

| # | 条件 | 確認対象 |
|---|------|----------|
| 1 | テスト仕様書にテストケースが追記されている | テストケース一覧に新規ケースが存在する |
| 2 | テストコードが実装されている | テストファイルが存在する |
| 3 | 全テストが合格している | 失敗 0・エラー 0 |
| 4 | カバレッジ証跡が成果物に格納されている | `coverage_<コンポーネント>/` のレポートが存在する |
| 5 | 実行ログ証跡が成果物に格納されている | `evidence/` のログが存在する |
| 6 | 実施結果一覧・結果サマリが更新されている | 報告書の該当セクションが最新である |
| 7 | カバレッジ実績が更新されている | 新規モジュールの数値が追記されている |
| 8 | Rubber-Duck レビューが完了している | `rubber-duck` エージェントを実行し、Blocking指摘がゼロである |
| 9 | Git にコミットされている | 上記すべてを満たした状態でコミットが作成されている |

## 工程完了時の自己批評（Rubber-Duck Agent）— 必須ゲート

> **WARNING:** 本セクションは省略不可。テスト実行・報告書更新後、Rubber-Duck を実行せずに
> 工程完了（次工程への遷移やコミット）してはならない。

### Rubber-Duck 実行手順

1. `task` ツールで `rubber-duck` エージェントを **必ず** 起動する
   - 利用できない場合は `code-review` または `general-purpose` エージェントで代替する
2. 以下の情報をプロンプトに含めて渡す:
   - レビュー対象ファイルパス（テスト仕様書・テストコード・テスト結果報告書・証跡ディレクトリ）
   - レビュー観点（以下4点を明記）:
     1. V字で対応する上流工程（詳細設計）の仕様が漏れなくテストでカバーされているか
     2. テスト結果と証跡が一対で揃い、証跡が成果物内に残されているか
     3. トレーサビリティ（詳細設計 → テストケース → 結果・証跡）に抜け漏れがないか
     4. 論理矛盾・考慮漏れ・偽陽性／偽陰性のリスクがないか
3. Rubber-Duck の出力（指摘事項）を確認し、Blocking 指摘があれば修正してから工程を完了とする
4. 指摘がない場合、または Non-Blocking のみの場合はその旨をコミットメッセージまたは報告書に記録する
