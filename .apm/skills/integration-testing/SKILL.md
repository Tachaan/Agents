# 結合テスト工程スキル（Integration Testing）

> 本スキルは **V字ウォーターフォール型開発を前提とした汎用工程ガイド** である。
> 成果物のパス・ファイル名・テスト/証跡コマンド・テストフレームワークは、適用するプロジェクトの
> 規約・技術スタックに合わせて読み替えること。本文中のパスやコマンドは推奨例であり、固定値ではない。

## V字モデルにおける位置づけ

結合テストはV字ウォーターフォールモデルの第2テスト工程です。対向設計工程は**基本設計**であり、
基本設計書に記載された機能間連携・IF仕様を検証します。

```
要件定義 ─────────────────────────────── システムテスト
    └─ 基本設計 ★ ────────────── 結合テスト ★
         └─ 詳細設計 ─────── 単体テスト
              └─ 実装 ─┘
```

## 成果物（汎用）

| 成果物 | 推奨パス（例） |
|--------|------|
| テスト仕様書 | `docs/<結合テスト>/ITS-XXX_結合テスト_テスト仕様書.md` |
| テスト結果報告書 | `docs/<結合テスト>/ITR-XXX_結合テスト_テスト結果報告書.md` |
| 証跡 | `docs/<結合テスト>/evidence/` |

### テスト仕様書の構成（標準）

- 文書管理 / 体制・スケジュール
- 環境・データ準備
- 観点・トレーサビリティ
- テストケース一覧 / 詳細
- IF一覧 / データ受渡し定義
- 結合シナリオ

## テスト対象（汎用）

### 代表的な結合ポイント

- **クライアント ↔ サーバAPI**: API経由の連携
- **アプリケーション ↔ データストア**: 永続化層のCRUD操作
- **アプリケーション ↔ 外部システム**: 外部サービス連携（実モック/スタブサーバーを使用）

### 関連IF仕様

- 外部IF仕様書 / 内部API仕様書（存在する場合）

## 作業ガイドライン

### 上流工程仕様書の参照（V字対応：基本設計）

結合テストはV字モデルで **基本設計** と対応する。基本設計書・IF仕様書を必ず参照し、
機能間連携・IF仕様・データ受渡しを結合シナリオとしてテストケースに落とし込むこと。

### テスト実行時

1. 外部連携がある場合は **モック/スタブサーバー** を起動して外部IF連携をテストする
   （MockBean等の差し替えではなく、可能な限り実プロトコルでの結合を検証する）
2. 結合テストは単体テストと分離したパターン/タグで実行する
3. クライアント↔サーバの結合はAPIレベルまたはE2Eで検証する
4. テスト結果はエビデンスとともに報告書に記録する

## 作業フロー（必須チェックリスト）

以下のステップを **上から順に** 実行すること。ステップを飛ばしてはならない。

---

### Step 1: 上流工程仕様書を参照し、結合ポイントを特定する

- 基本設計書を読み、機能間連携・データフローを把握する
- 外部IF仕様書・内部API仕様書で連携仕様を確認する
- 実装差分（直近のMerge Commitの変更ファイル）から今回テストすべき結合ポイントを特定する

---

### Step 2: テスト仕様書を更新する

**更新対象:** テスト仕様書（テストケース一覧）

**実施内容:**
- 新規テストケースを追記する（ID採番: 推奨 `TC-IT-XXX` の連番）
- 各行に以下を記入: テストケースID / テストグループ / テスト内容 / 観点 / 重要度 / 前提条件 / 期待結果概要 / テスト手法 / ステータス
- API間連携・データ永続化・外部IF呼出しの3観点を網羅すること
- 必要に応じて IF一覧・結合シナリオを更新する

---

### Step 3: テストコードを実装する

**実施内容:**
- プロジェクトの結合テストフレームワークでテストを実装する
  （例: JUnit + アプリ起動コンテキスト + HTTPクライアント）
- テストメソッド名・タイトルにテストケースIDを含める
- 実行順序の制御が必要な場合は順序付け機構を用いる
- 外部連携は実モック/スタブサーバーを使用する

---

### Step 4: テストを実行し、全件合格を確認する

- 外部連携がある場合はモック/スタブサーバーを起動する（別ターミナル / 非同期）
- 結合テストコマンドを実行する（単体テストと分離したパターン指定）
- **全件合格（失敗 0・エラー 0）** であることを確認する
- 1件でも失敗がある場合はテストコードまたは実装を修正して再実行する

---

### Step 5: 証跡を成果物ディレクトリ内に格納する

下記「証跡の収集手順」に従い、テスト実行ログを成果物ディレクトリにコピーし、
ファイルが存在することを確認する。

---

### Step 6: テスト結果報告書を更新する

**更新対象（必須）:**
- 実施結果一覧（ケースID / テストグループ / 実施日 / 結果 / 証跡パス）
- 結果サマリ（総件数・合格率・合否判定）
- 証跡一覧（証跡ファイルパスとケースIDの対応）

**必要に応じて更新:** 不具合一覧 / 外部IF結果・外部連携確認結果

---

### Step 7: Rubber-Duck Agent を実行する

下記「Rubber-Duck 実行手順」に従い、`rubber-duck` エージェントを起動してレビューを受ける。

---

### Step 8: 指摘事項を修正し、工程完了とする

- Blocking 指摘があればコード・ドキュメントを修正し、テストを再実行する
- 修正完了後、git commit する

---

> **WARNING:** Step 5（証跡格納）と Step 7（Rubber-Duck）を実行せずに工程を完了してはならない。

## 証跡の収集手順（汎用）

テスト実行後、生成された証跡を成果物ディレクトリ配下にコピーすること。

- **テスト実行レポート（XML/TXT）**: レポート出力先（例: `surefire-reports/`, JUnit XML）の
  結合テスト分を `docs/<結合テスト>/evidence/` にコピーする
- **カバレッジ（任意）**: 結合テスト実行時のカバレッジを併せて保存してもよい
- リクエスト/レスポンスログ・データストア状態・スクリーンショット等も証跡として保存する

証跡が成果物配下に存在することを確認してからテスト結果報告書を更新すること。
証跡が存在しない状態で報告書を更新してはならない。

## トレーサビリティ／証跡の一対管理

- 基本設計書の機能設計・IF設計 → テスト仕様書のテストケースへの追跡性を維持する
- テスト結果報告書と証跡は **必ず一対** で残し、各テストケースIDと証跡ファイルを対応付ける
- ファイル命名規則（推奨）: `ITS-XXX_<名>.md`（仕様書）/ `ITR-XXX_<名>.md`（報告書）

## 完了条件（Exit Criteria）

本工程は以下の **すべて** を満たした場合にのみ完了とする。1つでも欠けている場合は工程未完了である。

| # | 条件 | 確認対象 |
|---|------|----------|
| 1 | テスト仕様書にテストケースが追記されている | テストケース一覧に新規ケースが存在する |
| 2 | テストコードが実装されている | 結合テストに新規テストメソッドが存在する |
| 3 | 全テストが合格している | 失敗 0・エラー 0 |
| 4 | テスト実行ログが成果物に格納されている | `evidence/` にログが存在する |
| 5 | 実施結果一覧・結果サマリが更新されている | 報告書の該当セクションが最新である |
| 6 | 証跡一覧が更新されている | 証跡パスが追記されている |
| 7 | Rubber-Duck レビューが完了している | `rubber-duck` エージェントを実行し、Blocking指摘がゼロである |
| 8 | Git にコミットされている | 上記すべてを満たした状態でコミットが作成されている |

## 工程完了時の自己批評（Rubber-Duck Agent）— 必須ゲート

> **WARNING:** 本セクションは省略不可。テスト実行・報告書更新後、Rubber-Duck を実行せずに
> 工程完了（次工程への遷移やコミット）してはならない。

### Rubber-Duck 実行手順

1. `task` ツールで `rubber-duck` エージェントを **必ず** 起動する
   - 利用できない場合は `code-review` または `general-purpose` エージェントで代替する
2. 以下の情報をプロンプトに含めて渡す:
   - レビュー対象ファイルパス（テスト仕様書・テストコード・テスト結果報告書・証跡ディレクトリ）
   - レビュー観点（以下4点を明記）:
     1. V字で対応する上流工程（基本設計・IF仕様）の内容が漏れなくテストでカバーされているか
     2. テスト結果と証跡が一対で揃い、証跡が成果物内に残されているか
     3. トレーサビリティ（基本設計・IF仕様 → テストケース → 結果・証跡）に抜け漏れがないか
     4. 論理矛盾・考慮漏れ・偽陽性／偽陰性のリスクがないか
3. Rubber-Duck の出力（指摘事項）を確認し、Blocking 指摘があれば修正してから工程を完了とする
4. 指摘がない場合、または Non-Blocking のみの場合はその旨をコミットメッセージまたは報告書に記録する
